# МнеНеЖалко — Telegram-бот и Mini App

Бот книжного проекта [«МнеНеЖалко» в Польше](https://mnenezhalko.notion.site/in-Poland-e4f29a5687c449f79581add35f17791b):
быстрый доступ к общей библиотеке, поиск, ИИ-подбор книги по настроению,
городские чаты, ближайшие встречи, барахолка и добавление своей книги на полку.

Бот: [@mnenezhalkobot](https://t.me/mnenezhalkobot) · чат проекта: [МнеНеЖалко в Польше](https://t.me/+hlRk_HGIDcE4M2Vi)

## Что умеет

Дизайн Mini App — общая дизайн-система ISSA / KwadratPL (Telegram-нативные токены,
тёмная тема по умолчанию, плоские карточки, главная = хаб плашек).

## Данные

Библиотека живёт в публичном Notion проекта. Синхронизация — только на чтение,
через публичный `api/v3/queryCollection` (интеграционный токен не нужен):

- **КНИГИ** — 3 237 записей: название, автор, жанры, язык, обложка, владелец;
- **Библиотекари** — 141 человек: имя, город/район, Telegram, Instagram;
- **Настольные игры** — 12 записей.

Сервер Notion отдаёт максимум 1000 строк за запрос, поэтому книги забираются
рекурсивным делением диапазона «Date added» пополам (`server/src/notion.ts`).
Города приводятся к единому списку (`Gdańsk`/`Gdynia` → `Trójmiasto` и т. п.).

Полный синк занимает ~60 секунд, повторяется по расписанию
(`NOTION_SYNC_HOURS`, по умолчанию 12 ч), вручную — `npm run sync` или `/sync` от админа.
Книги, добавленные через бота (`source = bot`), синком не затираются.

## Как книга попадает в общую таблицу

[Инструкция новичка](https://mnenezhalko.notion.site/3fcdfa8ed57444d7ae2129bf5c0299f7)
просит человека завести себя в **Owners**, а книгу — в **All Books** (настолку —
в **Board Games**), войдя в Notion по почте. Бот делает это за него:

1. фото обложки → Claude vision → название, автор, язык, жанры
   (жанры и языки строго из справочников Notion, иначе multi-select засорится);
2. если библиотекаря ещё нет в Owners — заводится карточка с городом/районом
   («Warszawa/Wola» — город книги в All Books считается rollup'ом от владельца)
   и ссылкой на Telegram;
3. книга уходит строкой в All Books с обложкой-ссылкой `/api/cover/…`
   (то же «Embed link» из инструкции) и двусторонней связью с владельцем;
4. параллельно карточка живёт у нас, поэтому в поиске видна сразу.

Таблицы расшарены публичной ссылкой с правом `read_and_write`, но анонимно
Notion писать не даёт (`saveTransactions` → 401), поэтому нужен `NOTION_TOKEN_V2` —
cookie аккаунта, открывшего эту ссылку. Без токена или при сбое карточка остаётся
со статусом `pending`, админам приходит уведомление, дожать — `/notionpush`.

Проверить канал записи: `npm run notion:check -w server` — заводит тестовые строки
в Owners и All Books, читает их обратно и архивирует.

### Аккаунт для этой cookie

`NOTION_TOKEN_V2` — это сессия живого человека: она даёт доступ **ко всему**, что
видит аккаунт, а не только к таблицам проекта. Поэтому под неё нужен отдельный
служебный аккаунт, а не личный:

1. завести почту вида `bot@…` (подойдёт и алиас `+bot` к рабочей);
2. зарегистрировать на неё аккаунт Notion, ничего в него не складывать;
3. открыть с него публичную ссылку проекта — этого достаточно, чтобы cookie
   получила право писать в расшаренные таблицы;
4. DevTools → Application → Cookies → `token_v2` → в `.env` на VPS,
   `systemctl restart mnenezhalko`;
5. проверить: админская команда `/notion` покажет, под каким аккаунтом бот пишет.

Cookie живёт около года и слетает молча — при логауте или смене пароля. Бот
проверяет её при старте и раз в сутки: как только Notion перестал пускать,
админам приходит сообщение (и второе, когда доступ вернулся).

## «У кого моя книга сейчас»

Владелец вводит две вещи — название и ник читателя (`/lend Дюна | @anna`
или форма в Mini App). Дальше бот ведёт учёт сам:

- если книга нашлась на полке владельца, карточка привязывается и получает статус «занята»;
- срок по умолчанию — месяц, можно выбрать две недели или «без срока»;
- когда срок вышел, обеим сторонам раз в неделю прилетает мягкое напоминание;
- вернуть можно одной кнопкой — и владелец, и читатель закрывают запись сами,
  вторая сторона получает уведомление, книга снова «свободна».

Сверху экрана — сводка по настроению полки: сколько книг гуляет, какая ушла дальше
всех и как давно. Шкала одна для бота и Mini App (`loanMood` в `server/src/loans.ts`):

| Дней у читателя | | |
|---|---|---|
| 0–7 | 🙂 | первая неделя |
| 8–30 | 📖 | читают |
| 31–60 | 😐 | пора напомнить |
| 61–120 | 😟 | давно у читателя |
| больше 120 | 😢 | книга загостилась |

Если владелец назначил срок и тот прошёл, настроение портится быстрее календаря:
просрочка до недели — сразу «пора напомнить», до месяца — «давно у читателя»,
дольше — «загостилась». Так книга, отданная «на две недели», не выглядит спокойной
через месяц только потому, что месяц — это ещё немного.

Телеграм не даёт боту написать первым тому, кто с ним не общался. Поэтому у каждой
выдачи есть ссылка-приглашение `t.me/<bot>?start=loan_<id>`: владелец пересылает её
читателю, тот открывает бота, и выдача привязывается к нему (`claimLoans`).
Если читатель уже знаком боту, его id подхватывается сразу по нику — пересылать
ничего не нужно.

## Чат проекта: темы, афиши, барахолка

Общий чат — супергруппа `-1001856176764` с темами по городам. Их id зашиты
в `server/src/seed.ts` и заводятся при старте (идемпотентно, по url):

| Тема | id | Что делает бот |
|---|---|---|
| Warszawa 3637, Trójmiasto 3638, Kraków 3639, Wrocław 3640, Poznań 3641, Łódź 3642, Olsztyn 4875, Białystok 6999 | — | ссылки в `/groups` и в Mini App |
| Афиша встреч | 14501 | разбирает анонс (город, дата, место), заводит встречу, шлёт алерт подписчикам |
| Барахолка | 4547 | превращает пост с фото в карточку: тип, цена, город, кому написать |

История в Bot API недоступна: бот видит только сообщения, написанные после его
добавления. Старые объявления и афиши переносятся из выгрузки Telegram Desktop
(⋮ → «Экспорт истории чата» → JSON, с фото при необходимости):

```bash
npm run import -w server -- путь/result.json --mode market --topic 4547 --dry
npm run import -w server -- путь/result.json --mode market --topic 4547
npm run import -w server -- путь/result.json --mode events --topic 14501
```

`--dry` показывает, что получится, ничего не записывая; болтовня и сообщения
других тем отсеиваются, фото копируются в `data/covers`.

⚠️ Чтобы это работало, бот должен быть **участником группы** и **видеть сообщения**:
добавить @mnenezhalkobot в чат и либо выключить privacy mode
(@BotFather → `/setprivacy` → Disable), либо сделать бота администратором.
Пока бота нет в группе, темы просто показываются ссылками.

Анонсы приходят тем, у кого совпадает город (или город не выбран),
выключаются командой `/alerts`. Дубли отсекаются по id сообщения-афиши.

- `server` — TypeScript, Fastify 5, grammY, Prisma + SQLite, `@anthropic-ai/sdk`

## Запуск локально

```bash
cp .env.example server/.env  # единственный .env: сервер стартует из server/
npm install
npm run db:generate
npm run db:migrate -w server # создать SQLite-базу по миграциям (prisma/migrations)
npm run sync                 # первичный импорт из Notion (~1 мин)
npm run build -w web         # собрать Mini App
DISABLE_BOT=1 npm run dev    # API и Mini App без бота — обычный режим разработки
```

Mini App при разработке удобнее гонять отдельно: `npm run dev:web` (проксирует `/api` на 8080).

### Изменение схемы базы

Структура базы описана **миграциями** в `server/prisma/migrations`, а не подгоняется `db push`.
Порядок при правке `schema.prisma`:

```bash
# 1. сгенерировать миграцию из разницы «применённые миграции → новая схема»
npx prisma migrate diff --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "file:./data/shadow.db" --script \
  > prisma/migrations/<метка>_<имя>/migration.sql
# 2. дописать в файл перенос данных, если колонка должна быть заполнена не с нуля
# 3. проверить на КОПИИ прод-базы, а не только на пустой
npm run db:migrate -w server
```

Деплой применяет миграции сам (`scripts/db-migrate.sh`): на существующей базе без истории
принимает текущую схему как baseline, на пустой создаёт всё с нуля. ⚠️ Перед выкладкой миграции,
меняющей данные, снимите копию: `bash /opt/mnenezhalko/scripts/backup.sh` на сервере.

⚠️ **Рабочий токен бота на машине разработчика держать нельзя.** Бот в Telegram
один: `BOT_MODE=polling` делает `deleteWebhook` и молча забирает апдейты у прода —
живой бот замолкает, пока кто-нибудь не пожалуется. Нужен сам бот локально — заведите
своего у @BotFather. Предохранитель: увидев у токена чужой вебхук, сервер не стартует
и объясняет, что делать (осознанно перехватить — `ALLOW_STEAL_WEBHOOK=1`).

## Проверки

| Команда | Что проверяет |
|---|---|
| `npm run test -w server` | сервер: все `server/src/**/*.test.ts` (файлы находятся сами) |
| `npm run test -w web` | экраны Mini App: vitest + Testing Library |
| `npm run test:e2e` | **сквозной путь человека** в браузере |

Сквозные проверки (`e2e/`) поднимают настоящий сервер с чистой базой из
миграций и собранным Mini App и проходят весь путь: поставил книгу на полку →
нашёл в каталоге → выдал знакомому → второй человек встал в очередь → книга
вернулась → владелец оценил её. Telegram при этом не участвует: подпись
`initData` подделывается тестовым токеном бота, а SDK с telegram.org подменяется
заглушкой (иначе он затирает подставленный `window.Telegram` своим, с пустым
`initData`). Сеть не нужна: синк выключен (`NOTION_SYNC_HOURS=0`), справочник
жанров кладётся в базу заранее.

Первый запуск: `npx playwright install chromium`.

## Модерация участников

Правила сообщества и требования к доработкам — в `docs/MODERATION_POLICY.md`.
Коротко: есть глобальная блокировка (`User.accountStatus`) и **точечные** ограничения
(`UserRestriction`) — можно закрыть человеку отзывы, оставив полку, возвраты и очереди.
Проверка одна на весь проект (`server/src/moderation.ts::checkUserCan`) и стоит и в API,
и в боте: спрятанная кнопка в приложении защитой не считается.

Команды админа: `/moderation` (очередь разбора), `/restrict`, `/unrestrict`, `/ban`, `/unban`.
Ручки: `GET /api/admin/moderation`, `POST /api/admin/reviews/:id/decide`,
`POST /api/admin/users/:tgId/{restrict,unrestrict,ban,unban}`.

⚠️ Возврат книги и экран «Ваши данные» не ограничиваются никогда: первое закрывает
обязательство перед другим человеком, второе иначе превращало бы блокировку в удержание
чужих данных. Автобана нет: три жалобы прячут отзыв, человека ограничивает только человек.

## Персональные данные

Экран **«Ваши данные»** (`?screen=mydata`, вход из «О проекте») — что храним, зачем, на какой
срок, и две рабочие кнопки: забрать всё файлом и удалить себя из проекта. Текст на русском и
польском лежит в `web/src/privacy-text.ts`.

🔴 **Реквизиты контролёра данных там ПЛЕЙСХОЛДЕРЫ** (`{{DATA_CONTROLLER_NAME}}` и соседние).
Кто является контролёром и куда писать — решение владельца проекта, а не разработчика; пока не
подставлено, экран честно показывает «реквизиты ещё не заполнены».

Удаление (`server/src/mydata.ts`):

- то, что принадлежит только человеку (очереди, отзывы, жалобы, объявления, его фотографии),
  удаляется физически;
- закрытые выдачи **анонимизируются**, а не удаляются: у обмена две стороны, и стирать чужую
  историю нельзя;
- незакрытая выдача удаление **блокирует** — сначала возврат, иначе теряется след чужой книги;
- в журнале `DeletionRequest` остаётся только **отпечаток** Telegram id: HMAC-SHA256 с
  отдельным секретом `PRIVACY_DELETION_PEPPER`. Именно HMAC, а не sha256 от id: id это
  короткое предсказуемое число, простые хэши от него перебираются за секунды.
  ⚠️ Смена секрета обесценивает накопленный журнал — старые отпечатки перестают совпадать
  с кем-либо, и повторное применение по ним больше не сработает.

⚠️ **После восстановления резервной копии** обязательно прогнать повторное применение:

```bash
npm run privacy:reapply -w server -- /opt/backups/mnenezhalko/deletion-journal.csv
```

В старой копии снова лежат данные тех, кто просил их удалить. Журнал внутри самой копии тут
не поможет — в ней нет записей, сделанных позже; поэтому `scripts/backup.sh` ведёт журнал ещё
и отдельным **накопительным** файлом, который и передаётся аргументом.

Сроки хранения исполняет джоба `retention` (`server/src/retention.ts`, раз в сутки). Таблица
сроков на экране и константы в коде должны совпадать — при правке менять оба места.

| `NOTION_*` | id коллекций и вью Notion (значения по умолчанию уже верные) |


## Как устроен ИИ-подбор

1. Свободный текст → структурированный запрос (жанры строго из справочника, ключевые
   слова, язык) — structured outputs, `output_config.format`.
2. Кандидаты из базы по каждому жанру и слову → второй вызов выбирает до 5 книг
   и пишет, почему они подходят.
3. Ответ — карточки с контактом владельца.

Без ключа шаги 1–2 пропускаются, работает обычный поиск по словам.

## Выкладка

Прод живёт по симлинку: `/opt/mnenezhalko/current` → `releases/<sha>`. Данные и секреты
лежат отдельно и релизы переживают: `shared/data`, `shared/.env`.

```bash
bash scripts/release.sh          # взять артефакт CI для HEAD и выложить
bash scripts/release.sh --local  # собрать локально, если CI недоступен
```

Что происходит: артефакт (собранный в CI, без инструментов разработки) распаковывается в
`releases/<sha>` РЯДОМ с работающим релизом, туда ставятся только production-зависимости,
прогоняются миграции, и только потом `current` переставляется одной операцией
(`rename`). Дальше проверка живости: **не ответила — предыдущий релиз возвращается
автоматически**. Старые релизы чистятся, остаётся три.

Разовая подготовка сервера (уже сделана 30 июля 2026):
`bash scripts/release-setup.sh` — переносит данные и `.env` в `shared`, делает из прежнего
кода первый релиз и переводит systemd на `current`.

⚠️ `scripts/deploy.sh` (сборка на самом VPS, распаковка поверх живого каталога) **больше
не используется** и отказывается запускаться: он ломает симлинк-раскладку.

⚠️ **Правило миграций беты: они обязаны быть обратно совместимыми.** Откат симлинка
возвращает КОД, но не базу — миграции применяются к живой базе до переключения. Для
добавляющих изменений это нормально (прежний код просто не знает о новых колонках), а
разрушающие (удаление и перестройка таблиц) делаются отдельным согласованным релизом,
а не заодно. Страховка: перед миграциями выкладка снимает `shared/data/predeploy-<sha>.db`
(держатся два последних).

⚠️ Проверка живости сверяет **sha**, а не только «кто-то ответил»: `/api/health` отдаёт
`version` и `sha` из окружения релиза. Иначе переживший рестарт старый процесс ответил бы
бодрым `ok`, и выкладка сочла бы новый релиз успешным.

⚠️ `prisma` (CLI) намеренно лежит в `dependencies`, а не в `devDependencies`: на проде он
нужен для миграций и `prisma generate`, а всё остальное из инструментов разработки туда
не попадает (`npm ci --omit=dev`).

## Деплой (историческая справка)

`scripts/deploy.sh` — выкладка на VPS через `git archive | ssh` (см. комментарии в файле).
На сервере: `BOT_MODE=webhook`, `PUBLIC_URL=https://…`, systemd-юнит `mnenezhalko`.

### Прод

- Mini App: <https://mnenezhalko-46-224-220-94.sslip.io> (Caddy → `127.0.0.1:4310`)
- сервер: `root@46.224.220.94`, каталог `/opt/mnenezhalko`, юнит `mnenezhalko`
- логи: `journalctl -u mnenezhalko -f`
- ручной синк на сервере: `cd /opt/mnenezhalko && set -a && . server/.env && set +a && npm run sync`

⚠️ Локальный запуск с `BOT_MODE=polling` вызывает `deleteWebhook` и молча забирает
апдейты у прода. Для локальной работы либо заводите отдельного тестового бота,
либо поднимайте только веб-часть: `DISABLE_BOT=1 npm run dev`.
