# Дневник работ: МнеНеЖалко (бот + Mini App)

Подробная версия дневника: что сделано, зачем, почему именно так, и чем это проверено.
Человеческая версия для заказчика лежит рядом: `docs/mnenezhalko-diary.html`.
Свежее сверху внутри каждого дня; дни идут по возрастанию, чтобы читалась логика развития.

Прод: https://mnenezhalko-46-224-220-94.sslip.io (бот @mnenezhalkobot)
Код: TypeScript, Fastify 5 + grammY + Prisma/SQLite, web = React 18 + Vite
Репозиторий: https://github.com/ipostatos/mnenezhalko

---

## Как ведётся эта работа (три правила, которые объясняют почти все решения ниже)

1. **Проверять на живом, а не на бумаге.** Каждое изменение инфраструктуры и каждая правка
   безопасности проверяется реальным прогоном на проде (curl, логи, замер), а не только чтением
   кода. Причина: на соседнем проекте скрипт деплоя, «правильный по логике», уронил прод на 8 часов.
2. **Каждый баг сначала воспроизвести тестом.** Потом починить. Потом откатить починку и убедиться,
   что тест падает. Тест, который не падал до фикса, не охраняет ничего: он лишь фиксирует, что
   функция существует.
3. **Данные принадлежат проекту, а не приложению.** Источник правды по книгам это открытая таблица
   Notion, которую ведут люди. Приложение читает её и умеет писать, но не подменяет собой.

## 22 июля 2026. Запуск в прод и первый аудит

### Развёртывание
- VPS, systemd-юнит `mnenezhalko`, порт 4310, Caddy как фронт с TLS.
- Служба работает **от отдельной учётки** `mnenezhalko` (не root), с `NoNewPrivileges` и
  `ProtectSystem=full`, пишет только в `server/data`.
  *Зачем:* компромисс бота не должен становиться компромиссом сервера.
- `.env` принадлежит `root:mnenezhalko` с правами `640`.
  *Почему так:* файл читает systemd при старте, а служба должна иметь право чтения, но не записи.
  Без этого Prisma ловит `EACCES`.
- Бэкап `scripts/backup.sh` (база + обложки + `.env`, хранение 14 дней) в кроне root в 3:34.
  Проверено восстановлением, а не только фактом создания архива.
- ⚠️ Грабля: `.gitattributes` держит `*.sh` и `*.service` в LF. Без этого `git archive` с Windows
  отдаёт CRLF, и скрипт на сервере просто не стартует.

### Фото книги как основной способ добавления
Фото обложки уходит в Claude vision, оттуда название, автор, язык, жанры. Карточка на
подтверждение, затем запись владельца в Owners и книги в All Books.

*Зачем:* библиотека растёт только если добавить книгу проще, чем не добавить. Форма на 6 полей
убивает поток.

⚠️ Грабля: Anthropic SDK с картинками падает `APIConnectionError` на Windows/Node 25 (сырой fetch
тем же телом проходит), на VPS (Node 22) работает. Вывод: vision локально не тестировать.

### Запись в Notion
Таблицы расшарены на запись, но анонимно писать нельзя (`saveTransactions` отдаёт 401), поэтому в
проде лежит cookie личного аккаунта (`NOTION_TOKEN_V2`).
*Почему так, а не «официально»:* официальный API не покрывает нужные операции для этих таблиц.
Плата за это: cookie живёт около года и слетает при смене пароля, поэтому появился сторож
(проверка при старте и раз в сутки, сообщение админам при поломке и при возврате в норму, негативный
путь проверен подменой токена).
🔴 Долг: служебный аккаунт Notion вместо личного.

### Бот отвечал на один вопрос десятками сообщений
*Причина:* дефолт grammY `webhookCallback` (`onTimeout: 'throw'`, 10 секунд). ИИ-подбор не
укладывался в 10 секунд, вебхук отдавал 500, Telegram повторял апдейт около двух часов, и каждый
повтор давал новый ответ.
*Лечение:* `{ onTimeout: 'return', timeoutMilliseconds: 8000 }`, дедуп по `update_id` (15 минут),
single-flight на ИИ-подбор по пользователю, `setWebhook(..., drop_pending_updates: true)`.
*Диагностика на будущее:* 500 на `/tg/webhook` в `journalctl` и `pending_update_count` в
`getWebhookInfo`.

### Аудит безопасности (первый, внутренний)
- Вебхук требует `secret_token` (выводится из `BOT_TOKEN`). До этого подделкой `from.id` можно было
  выполнить админские команды и разослать анонс всем участникам.
- `/api/ai` и `/api/recognize` только по подписи Telegram + лимит на человека. До этого `/api/ai`
  был открыт всему интернету, а ключ Anthropic **общий с другим проектом**: чужой трафик оплачивался
  бы из общего кошелька.
- `isAdmin` перестал «залипать» в базе: единственный источник правды это `ADMIN_IDS` в окружении.
- Локальный запуск с `BOT_MODE=polling` делает `deleteWebhook` и молча забирает апдейты у прода.
  Добавлен предохранитель: увидев у токена чужой вебхук, сервер не стартует
  (осознанный обход `ALLOW_STEAL_WEBHOOK=1`).

### Технический долг того же дня
Кэш справочников (119 мс, стало 2 мс), поиск ранжирует весь набор совпадений (до 500) и режет на
страницы после, CI на GitHub Actions (типы сервера + сборка web + `npm audit`).

## 24 июля 2026. Стабилизация PL: план из восьми задач

Принцип, заданный заказчиком: сначала довести польскую версию до стабильной, потом масштабировать.
Восемь задач оформлены как GitHub Issues с зависимостями и критериями приёмки. Порядок не случаен:
первая задача это фундамент, остальные на ней стоят.

### 1. Единая идентификация библиотекаря (корень)
*Симптом:* полка библиотекаря пуста, хотя книг 91. Плюс дубли библиотекарей в списке.
*Причина:* `putOnShelf` искал человека по `tgId`, а синхронизация заводила его по `notionId` без
`tgId`. Получались две записи на одного человека, и Telegram-аккаунт висел на пустой.
*Решение:* `librarian.ts::linkLibrarian()` как единая точка опознания (tgId, затем нормализованный
ник с привязкой tgId, затем создание). Через неё ходят все пути: `putOnShelf`, `/api/me`,
`/api/my-books`, `/lend`.
*Миграция:* `npm run migrate:librarians` сливает дубли на главную запись, переносит книги,
привязывает `tgId`, архивирует дубль через `mergedIntoId`.
*Главный риск и как закрыт:* синхронизация могла вернуть книги назад на архивный дубль. Поэтому
sync резолвит `mergedIntoId` в `ownerByNotion`. Проверено реальным прогоном на копии dev-базы.
*Порядок на проде:* deploy (`db push`) → backup → stop → миграция → chown → start. Бэкап
`20260724-1551`.

### 2. Автообновление Telegram-контакта
При смене ника контакт правится сразу локально, отправка в Notion идёт в фоне. При сбое ставится
флаг `telegramSyncPending`, дожимается в синке, админам уходит сообщение. Синхронизация не
перезаписывает контакт у записей с невыполненной отправкой (иначе Notion затирал бы свежий ник).

### 3. Модерация книг
`reviewStatus` (pending / approved / rejected / deleted) **отдельно** от `notionStatus`.
*Почему отдельно:* «одобрена ли книга людьми» и «доехала ли она до Notion» это разные оси, и
смешивать их значит рано или поздно показать в каталоге неодобренное или потерять одобренное.
За флагом `MODERATION_ON` (включён на проде). Каталог фильтрует `approved` везде: поиск, карточка,
справочники, дайджест, профиль, счётчики, health.

### 4. Моя полка
Экран со всеми шестью состояниями (`shelfState()`), правка с отправкой в Notion, мягкое удаление
(`active=false` + `reviewStatus=deleted` + архивация строки), книга на руках не удаляется сразу, а
скрывается при возврате (`hideAfterReturn`). Все мутации: подпись Telegram + проверка владельца.

### 5. Проверка дублей книг
Ключ: владелец + нормализованное название/автор + тип. `own` (свой повтор) даёт предупреждение и
подтверждение при сохранении, `others` (чужой экземпляр) это подсказка, а не блок.
*Почему не блокировать чужие:* два экземпляра одной книги у разных людей это норма для
библиотеки, а не ошибка.

### 6. Кэш Mini App
*Найдено:* у `@fastify/static` при `cacheControl:false` его же `setHeaders` **не применяется**,
поэтому заголовки ставит единый `onSend`: `/api/*` no-store (кроме обложек со своим immutable),
`/assets/*` immutable, `/il/*` сутки, `index.html` no-store. Клиент шлёт `cache:'no-store'` и
перезапрашивает данные при возврате из фона (`visibilitychange`).
*Зачем:* Telegram держит вебвью в памяти, и без этого человек добавлял книгу, а на полке её не видел.

### 7. Подтверждение возврата, история, undo
Возврат в два шага, окно отмены 24 часа, модель `LoanEvent` (created / claimed / reminded /
returned / reopened / cancelled) как журнал событий выдачи.
*Зачем журнал:* без него «кто и когда отметил возврат» восстановить невозможно, а спорные случаи
в библиотеке обмена неизбежны.

### 8. Тесты напоминаний
Ядро `runOverdueReminders` вынесено из бота (без grammY), с инъекцией `now` и адаптера отправки.
10 сценариев на временной SQLite. Сбой отправки одному не срывает рассылку остальным.

### Дизайн-рефреш (в тот же день, отдельным заходом)
Фирменная палитра заказчика вместо тёмной темы ISSA: крем `#f7f1e8`, акцент персиковый `#eba788`
(цвет волос девочки с иллюстраций; путь итераций: индиго → лаванда → терракота → персик),
единый градиент персик-шалфей, иллюстрации заказчика, иконки Lucide вместо кустарных SVG.
Только визуальные изменения, функции не тронуты.
⚠️ Для этого приложения фирменная палитра **заменяет** общий стандарт ISSA: не откатывать.

## 25 июля 2026, первая половина. Скорость, импорт, внешний аудит

### Конвейер обложек
*Проблема по слоям, а не одна:* большинство обложек это прямые ссылки на чужие хосты (livelib,
azbooka, amazon, прокси Notion), оригиналы по 1 до 3 МБ; витрина карусели грузила 80 книг сразу;
подборка была новой случайной на каждый заход; в карусели на каждом кадре читались офсеты всех
40 элементов (forced reflow).

*Сделано:*
- `imgcache.ts`: `proxyCover(url, w)` даёт подписанный `/api/img?u=…&w=…&s=<HMAC>`. Подпись
  покрывает **и ширину**, иначе это открытый ресайзер и SSRF-вектор.
- `/api/img` ресайзит через **sharp** в webp-превью нужной ширины, кладёт на диск, дальше immutable.
- Дедуп in-flight (N запросов одной обложки это одна загрузка), лимит 4 одновременных внешних
  скачивания, негативный кэш 1 час для битых.
- Метрики в ответе: `X-Image-Cache`, `X-Image-Origin`, `Server-Timing: img;dur=`.
- Витрина 80 → 12 книг, стабильна 30 минут (memo по городу на сервере).
- Карусель: офсеты меряются один раз, центр и два соседа eager с высоким приоритетом, остальные
  lazy, `will-change` только у близких к центру, skeleton до загрузки.

*Замер на проде:* azbooka 971 КБ → webp 320 = 46 КБ (минус 95%), MISS 748 мс → HIT 2 мс.
⚠️ Прежняя оценка «50 до 500 раз» была локальным микрозамером одного файла, а не p50/p95 у
пользователей. Теперь для честного замера есть заголовки.

### Пакетный импорт
- Telegram-альбом: фото с общим `media_group_id` копятся с дебаунсом 1.5 с и обрабатываются пачкой,
  в конце одна сводка (до 10).
- `/import` со списком «Название — Автор» построчно (до 30).
- ISBN: `isbn.ts::lookupIsbn()`, **OpenLibrary первым** (`jscmd=data`, отдаёт авторов именами),
  Google Books запасным.
  *Почему такой порядок:* Google Books без ключа отдаёт 429 даже с прод-IP.
  ⚠️ Русские издания в OpenLibrary покрыты плохо, часто `null`.
- Добавление админом **от имени** библиотекаря: `putOnShelf` получил `ownerLibrarianId` (книга
  принадлежит цели, `addedByTg` это админ для аудита, город берётся у цели), команда
  `/onbehalf @ник`, сброс `/onbehalf off`.

🔴 Ботовые команды юнит-тестами не покрыты (нужен реальный Telegram и vision), ждут живой проверки.

### Внешний аудит: три P0
1. **Выдача чужой книги.** `createLoan()` брал `bookId` из тела на веру. Теперь в
   `prisma.$transaction`: проверка владельца (`book.owner.tgId === ownerTg`), `approved`, свобода
   книги и отсутствие второй активной выдачи.
2. **Частичный Notion-sync мог скрыть половину библиотеки.** `deactivationGuard`: при объёме ≥20 и
   «пропаже» >15% деактивация пропускается, синк помечается подозрительным, админам уходит
   предупреждение.
3. **SSRF через coverUrl.** `net.ts`: `isPrivateIp` / `assertPublicUrl` (резолв DNS + проверка всех
   адресов и на каждом hop редиректа, `redirect:'manual'`) / `isSafeCoverUrl` на приёме.
   ⚠️ Грабля: `isPrivateIp(host)` на **имени** домена вернул бы true. Литеральный IP проверять по
   маске, имя по результату DNS.
4. **sharp 0.33 → 0.35.3** (libvips CVE-2026-33327 / 33328 / 35590 / 35591).

## 25 июля 2026, вторая половина. Сессия стабилизации (этапы 0 до 9) и выход в прод

Отдельный заход по большому плану заказчика: сначала стабилизация, потом фичи. Тестов было 18,
стало **96**. Каждый пункт ниже это не «сделал по чеклисту», а найденный баг с воспроизведением.

### Полный жизненный цикл обложек
- **`/api/loans` отдавал сырой `book.coverUrl`** мимо всего конвейера: без ресайза, без кэша и
  **без SSRF-проверки**. Теперь через `withCoverProxy`.
- **Один размер 640px на всё** заменён на реальные размеры отрисовки из styles.css:
  `LIST_W=96`, `CARD_W=220`, `CAROUSEL_W=320`. Варианта «full» нет: крупнее 128px CSS обложка в UI
  не показывается нигде.
- **Фото пользователя сохранялось сырым: без EXIF-strip и без rotate,** а ссылка публичная и уходит
  в общий Notion, то есть GPS с телефона утекал. Теперь `covers.ts::normalizeForStorage`
  (rotate по EXIF → resize 1600 → webp, метаданные не переносятся).
  ⚠️ GIF не трогаем: resize без `{animated:true}` схлопнул бы анимацию в один кадр.
- **Лимит размера проверялся после полного `arrayBuffer()`:** origin без `Content-Length` мог залить
  гигабайты в память до отказа. Теперь `readLimited` считает байты по стриму и рвёт соединение.
- **Кэш превью не чистился вообще** (на проде 181 МБ, 1510 файлов, 0 эвикшена). `housekeepImgCache`
  (60 дней / 2 ГБ, таймер 6 часов) не трогает файлы младше 5 минут, чтобы не удалить недописанную
  запись.
- **Витрина прогревалась первым посетителем** → `warmShowcaseCovers` в фоне на новую ротацию.

### Инварианты выдач
- **`reopenLoan` (undo) содержал реальную гонку:** проверка «не выдана другому» и запись были
  разными запросами, конкурентный `createLoan` пролезал между ними, и на книге оказывались **две
  активные выдачи**. Воспроизведено тестом (2 !== 1), закрыто транзакцией.
- **`markReturned` тоже не был транзакционным:** падение между шагами оставляло книгу занятой
  навсегда, без выдачи.

### Claim-токены (дыра в ссылках-приглашениях)
*Было:* ссылка `?start=loan_<id>` содержала сырой `loan.id`, который публичен и светится в API,
событиях и Notion. При этом `claimLoans()` запускался при **каждом** `/start` и по совпадению
username забирал **все** чужие невостребованные выдачи. Зарегистрировав в Telegram чужой
освободившийся ник, человек одним `/start` получал чужие книги и право отметить их возвращёнными.
*Стало:* `Loan.claimTokenHash` (unique) + `claimTokenExpiresAt`, токен 24 байта, в базе только
sha256, `claimLoanByToken` привязывает **ровно одну** выдачу, при несовпадении username отказ.
Legacy-ссылки работают только для выдач без токена и только при совпадении ника.
`issueClaimToken` перевыпускает токен для напоминаний.

### Предохранитель синка перестал маскировать сам себя
*Было:* подозрительный прогон всё равно двигал «последний успешный» baseline, то есть скрывал ровно
то, ради чего предохранитель и делался.
*Стало:* baseline двигается только при `booksOk && gamesOk && !suspicious`. Плюс books и games стали
независимыми (падение games не срывает уже прочитанные books, у упавшего источника деактивация
пропускается целиком). Пороги в env: `NOTION_SYNC_GUARD_MIN/PCT`.

### DNS rebinding (TOCTOU)
*Было:* `assertPublicUrl` резолвил DNS сам, а `fetch()` потом резолвил хост **второй раз**.
Атакующий DNS с TTL=0 отдаёт публичный адрес на проверку и приватный на соединение: проверка
проходит, соединение уходит внутрь сети.
*Стало:* `assertPublicUrl` **возвращает** проверенные адреса, а `imgcache.ts::pinnedAgent`
(undici `Agent` с `connect.lookup`) подключается именно к ним.
*Проверено эмпирически:* подмена lookup на 127.0.0.1 реально даёт ECONNREFUSED, то есть пиннинг
работает, а не игнорируется. ⚠️ Добавлена зависимость `undici` (движок, на котором и так работает
встроенный fetch).

### Наблюдаемость и бюджеты
- `X-Image-Cache` различает HIT / MISS / **NEGATIVE** (раньше всё было «MISS»), плохая подпись это
  400, а не 404.
- Структурные логи (host, ширина, байты, категория ошибки) **без полного URL**: в query чужих CDN
  бывают их собственные токены.
- Админская ручка `GET /api/admin/img-metrics`: счётчики, bucketed-длительности, разбивка ошибок
  origin, размер кэша.
- `showcase-budget.test.ts` через `app.inject` на реальном Fastify: дефолт ≤12, clamp до 16, ключ
  кэша учитывает лимит, обложки идут через `/api/img?w=320`. Регресс к 80 книгам или к оригиналам

### Фоновый синк не запускался вовсе
*Найдено на проде:* `lastSync` показывал 25 часов при заявленном периоде 12.
*Причина:* `setInterval` отсчитывался от старта процесса, а деплой это рестарт. При нескольких
деплоях в день 12-часовой отсчёт сбрасывался раньше, чем доходил до конца, и фоновая синхронизация
не отрабатывала **ни разу**. Ничего не падало: данные просто тихо старели.
*Стало:* `nextSyncDelayMs(lastSync, now, syncHours)` считает срок от последней **успешной**
синхронизации (`syncState`), просроченная идёт через загрузочную паузу 30 секунд (сначала подняться
и начать отвечать, потом идти в Notion).
*Ловушка в собственном решении:* неудачный и подозрительный прогоны не двигают `lastSync`, поэтому
планирование «от lastSync» само по себе давало бы срок в прошлом, то есть повтор каждые 30 секунд и
непрерывный долбёж Notion. Отсюда `retryDelayMs`: 15 / 30 / 60 минут, но не дольше периода.
«Удачным» считается только прогон, продвинувший baseline (то же условие, по которому health
показывает `lastSync`).
*Проверено на проде:* синхронизация поднялась через 30 секунд после рестарта, `lastSync`
продвинулся, следующий прогон запланирован через 720 минут, библиотекарей стало 143.
7 тестов на планирование, включая «битая или будущая метка не блокирует синк навсегда».

### Приватность контактов (этап 9.2)
*Решение продукта (заказчик, 25 июля):* каталог остаётся публичным, контакты закрываются подписью.
*Почему именно так:* книги и так лежат в открытой таблице проекта, прятать их бессмысленно и вредно
для будущих витрин и ссылок. А вот контакты это личное.
*Что было:* `GET /api/books`, `/api/books/:id`, `/api/librarians/:id` и дайджест отдавали
Telegram-ник и инстаграм владельца **без всякой авторизации**: базу контактов всех 143
библиотекарей можно было забрать одним `curl`.
*Найдено сверх заявленного:* `GET /api/market` отдавал **сырые строки таблицы**, то есть числовой
`authorTg` и ник каждого, кто когда-либо публиковал объявление. То же с `createdBy` у встреч.
*Сделано:* `server/src/privacy.ts` (`redactOwner` / `redactCard(s)` / `redactMarketItem` /
`redactEvent`), применено в `/api/books`, `/api/books/:id`, `/api/librarians/:id`, `/api/digest`,
`/api/market`, `/api/events`. Контакты только при валидной initData. **Числовые tgId не уходят
клиенту вообще, даже подписанному:** писать человеку можно только по нику, а по числовому id бот
может писать первым, то есть это внутренний идентификатор, а не контакт.
*Поля не удаляются, а становятся `null`:* у клиента типы `string | null`, условие `owner.telegram &&`
просто не покажет кнопку. Удаление ключей заставило бы фронт различать «нет ника» и «ник скрыт»,
хотя ведёт он себя одинаково.
*CORS:* `origin: true` (отражение любого Origin) заменён на собственный origin. Mini App живёт на том
же домене, что и API, а в dev у vite стоит proxy на `/api`, поэтому кросс-доменные запросы не нужны
никому из своих.
*Тесты:* `privacy.test.ts`, 9 штук на реальном Fastify через `app.inject`. Ключевой не «поле скрыто
у книги», а **сплошное сканирование ответов всех публичных ручек** на утечку ника, инстаграма и
числового id: новая ручка, автор которой забыл про redact, свалит тест.
*Проверено откатом:* снял redact у барахолки, упали 2 теста из 9, вернул.
*Проверено на проде:* анонимно `telegram: null` при 1768 книгах в Варшаве; с валидной подписью
(сгенерил на VPS из прод-токена) ники отдаются; чужой Origin не получает `Access-Control-Allow-Origin`,
свой получает.

## Грабли, которые стоит помнить

- Деплой только с `chown -R mnenezhalko:mnenezhalko` на `server/data`.
- Деплой деплоит HEAD: сначала коммит, потом деплой.
- Локальный запуск в режиме polling забирает апдейты у прода. Локально поднимать только веб-часть
  (`DISABLE_BOT=1`).
- На Windows `prisma generate` падает `EPERM`, если живы осиротевшие процессы `tsx watch` (держат
  `query_engine.dll`). Лечение: убить их, потом generate. Проверено чистым клоном: в изолированной
  среде все команды проходят, то есть это среда, а не код.
- `db push` требует `--accept-data-loss` при добавлении unique-колонки, даже если данных нет.
- `.cover-carousel` обязан быть `position: relative`, иначе `offsetLeft` детей меряется от далёкого
  предка и центрирование врёт.
