# Мониторинг: два слоя, которые сторожат друг друга

Слоя два, и они закрывают разные классы поломок:

| Слой | Где живёт | Видит | Слеп к |
| --- | --- | --- | --- |
| **Внутренний watchdog** | на той же машине, systemd-таймер раз в час | тихие поломки внутри работающего приложения: зависшие письма, ошибки джоб, диск, бэкап, cookie Notion | смерть машины, пропажа сети, поломка Telegram API |
| **Внешний монитор** | расписание GitHub Actions, раз в 10 минут | всё, что видит человек с телефона: сервер не отвечает, сертификат, белый экран Mini App | тихие внутренние поломки, собственное выключение |

Ни один из них не заменяет другой. Чтобы не осталось и третьей дыры — «сторож
молча выключился» — они проверяют друг друга: внешний монитор после удачного
обхода отмечается в приложении (`POST /api/monitor/ping`), а внутренняя проверка
поднимает инцидент, если снаружи не заходили дольше трёх часов.

# Внутренний watchdog: что он видит и чего не увидит

Появился 30 июля 2026 вместе с неделей наблюдения (`OBSERVATION_GATE.md`).
Это **внутренний** слой контроля: он живёт на той же машине, что и приложение.

## Что это такое

Раз в час systemd-таймер запускает проверку `scripts/observe-local.sh` и, если та
нашла инцидент, `scripts/observe-alert.sh` пишет администраторам в Telegram.

| Файл | Роль |
| --- | --- |
| `scripts/observe-local.sh` | Сама проверка. Работает на сервере, только читает: ни записи в базу, ни рестарта. Код возврата 1 — есть инцидент |
| `scripts/observe.sh` | Обёртка для ручного запуска с рабочей машины по SSH (`bash scripts/observe.sh`) |
| `scripts/observe-alert.sh` | Watchdog: прогон проверки, решение писать или молчать, отправка |
| `scripts/mnenezhalko-observe.service` | Единичный прогон, `SuccessExitStatus=0 1` (инцидент это не сбой проверки) |
| `scripts/mnenezhalko-observe.timer` | Раз в час, `Persistent=true`, `OnBootSec=5min`, `RandomizedDelaySec=3min` |

## Что он увидит

- служба не `active` или её перезапускал systemd (то есть процесс падал);
- `/api/health` не отвечает;
- письма о решениях модерации не доставлены после трёх попыток;
- книга зависла в `approving` дольше 30 минут;
- джоба планировщика записала ошибку;
- cookie Notion не работает или синк не проходил больше суток;
- свободного места меньше 800 МБ (релизы запрещены) или меньше 1,5 ГБ (предупреждение);
- бэкап старше 26 часов или его нет вовсе.

## Чего он НЕ увидит — и это важно

- **Смерть всей машины.** Нет машины — нет и проверки: никто не напишет.
- **Пропажу сети или блокировку исходящих.** Проверка пройдёт, отправка молча не дойдёт
  (в journal останется «не смог написать админу»).
- **Поломку самого Telegram API.** Тот же случай: отправить сообщение нечем.
- **Проблемы, которые видны только человеку**: сломанная вёрстка, неудачная формулировка,
  бот отвечает не то. Это ловится глазами и жалобами.

Именно ради этих случаев рядом появился **внешний монитор** (следующий раздел).
Внутренний watchdog его не заменяет и не отменяет — он закрывает другой класс:
тихие поломки внутри работающего приложения, о которых иначе узнаёшь через неделю.
Плюс с 30 июля он проверяет самого внешнего монитора: раздел «внешний монитор»
в отчёте показывает, когда снаружи заходили в последний раз.

## Сломанная проверка — это инцидент

Поймано в первый же час работы на проде: скрипт проверки приезжает из архива релиза
без exec-бита, прямой запуск падал `Permission denied`, отчёт получался пустым, строк «🔴»
в нём не было — и watchdog честно писал в journal «норма, молчу». Мониторинг, который
выглядит здоровым при неработающей проверке, хуже отсутствующего.

Поэтому: проверка запускается через `bash` (exec-бит не нужен), а её код возврата больше 1
или пустой отчёт превращаются в инцидент «проверка наблюдения не выполнилась» и уходят
администраторам. Есть тесты на оба случая.

## Молчание важнее сообщений

Watchdog, который пишет каждый час об одном и том же, выключают на третий день,
и тогда он не сообщит уже ничего. Правила:

| Переход | Что делает |
| --- | --- |
| норма → инцидент | пишет сразу |
| тот же инцидент продолжается | молчит |
| тот же инцидент, 6 часов без решения | напоминает один раз, дальше снова молчит |
| набор инцидентов изменился (добавился новый) | пишет сразу |
| инцидент → норма | пишет один раз «снова в норме» |

Состояние лежит в `/opt/mnenezhalko/shared/monitoring/observe-state`: отпечаток строк
инцидентов, время начала и время последней отправки.

⚠️ Отпечаток считается по строкам «🔴» **с выбитыми числами**: «бэкап 29 ч назад»
и «бэкап 30 ч назад» это одна и та же проблема. Без этого каждый час приходило бы
сообщение «набор инцидентов изменился», то есть ровно тот спам, от которого правила и защищают.

## Что уходит в Telegram

```
🔴 МнеНеЖалко: инцидент наблюдения

• не доставлено писем о решениях после трёх попыток: 1
• последний бэкап 29 ч назад (cron в 3:34)

Релиз: 1e29b10
Версия: 0.2.0-beta.2
Время: 30.07.2026 09:45 Europe/Warsaw

Проверка:
systemctl status mnenezhalko
journalctl -u mnenezhalko -n 100
```

Только агрегаты и техника релиза. **Не уходит ничего личного**: ни имён, ни ников,
ни числовых id, ни текстов отзывов, ни причин ограничений, ни текста `lastError`
(там может оказаться название книги или ник — Telegram возвращает такое в ошибках).
Подробности печатаются обычными строками: они остаются в отчёте и в `journalctl`,
но в сообщение не попадают. На это есть отдельный тест.

Сообщение уходит **каждому** администратору независимо: недоставка одному
(заблокировал бота, не начинал диалог) не отменяет отправку остальным.

## Установка на сервере

Юниты ставятся один раз, дальше они подхватывают скрипты текущего релиза через
симлинк `current`:

```bash
install -d -m 755 /opt/mnenezhalko/shared/monitoring
cp /opt/mnenezhalko/current/scripts/mnenezhalko-observe.service /etc/systemd/system/
cp /opt/mnenezhalko/current/scripts/mnenezhalko-observe.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now mnenezhalko-observe.timer
```

Проверить:

```bash
systemctl list-timers mnenezhalko-observe.timer   # когда следующий запуск
systemctl start mnenezhalko-observe.service       # прогнать сейчас
journalctl -u mnenezhalko-observe -n 50           # что увидел
```

Разовый прогон вручную с рабочей машины (без отправки сообщений):
`bash scripts/observe.sh`.

# Внешний монитор: проверка снаружи

Появился 30 июля 2026. Живёт **не на нашей машине**: расписание GitHub Actions
(`.github/workflows/uptime.yml`) раз в 10 минут запускает `scripts/uptime-check.mjs`
и стучится в прод по публичному адресу — так же, как это делает человек с телефона.

Зависимостей у проверки нет намеренно: она не ставит `npm ci` и не собирает проект.
Монитор должен подниматься даже тогда, когда со сборкой репозитория что-то не так.

## Что он проверяет

| Проверка | Почему именно она |
| --- | --- |
| `/api/health` отвечает 200 и это JSON с `ok:true` | код 200 сам по себе ничего не значит: заглушка хостинга и чужой Caddy-блок тоже отвечают 200 |
| книг в каталоге не меньше 100 | приложение может отвечать бодро с пустой или подменённой базой |
| главная Mini App открывается и в ней есть ссылка на собранный скрипт | выложенная мимо релиза страница без сборки — это белый экран у всех |
| сам скрипт из `/assets/` отдаётся 200 | самый частый вид «сайт работает, а приложение нет» |
| срок сертификата | Caddy обновляет сам, и ломается это тихо: 14 дней — предупреждение, 3 — инцидент |
| время ответа | медленнее 2,5 с — предупреждение, не побудка |

Одна неудачная попытка инцидентом не считается: проверка повторяется до трёх раз
с паузой 15 секунд. Иначе людей будил бы каждый разрыв соединения у бегуна GitHub.

## Как он будит людей

1. **Упавшая джоба.** GitHub сам пишет письмо владельцу репозитория — работает
   без единой настройки, поэтому это базовый сигнал.
2. **Сообщение в Telegram** — если заданы секреты `MONITOR_BOT_TOKEN` и `MONITOR_CHAT_ID`.

⚠️ Для тревог заводится **отдельный бот**, а не рабочий `@mnenezhalkobot`. Токен
рабочего бота не должен лежать во второй системе: утечка секрета GitHub тогда
означала бы захват бота. Отдельный бот умеет ровно одно — писать в один чат.

Правила молчания те же, что у внутреннего watchdog'а, но состояние хранить негде:
у расписания нет своей памяти. Поэтому решение выводится из **истории прошлых
запусков** — её GitHub помнит сам:

| Переход | Что делает |
| --- | --- |
| прошлый запуск зелёный, сейчас инцидент | пишет сразу |
| прошлый тоже красный | молчит |
| красный уже 6 часов | напоминает один раз |
| был красный, стал зелёный | пишет «снова отвечает» |

Отменённые и пропущенные запуски (GitHub отменяет их при перегрузке очереди) не
считаются ни падением, ни нормой: иначе посреди аварии пришло бы «снова в норме».

## Ручной прогон — это диагностика, а не наблюдение

Запуск руками (`gh workflow run uptime.yml`) и запуск по расписанию делают одну
и ту же проверку, но в состоянии наблюдения участвует только расписание. Смешивать
их нельзя в обе стороны:

- ручной зелёный прогон посреди аварии выглядел бы «предыдущий запуск успешен»,
  и следующее расписание прислало бы **вторую** тревогу об одном и том же;
- ручной прогон против заведомо сломанного адреса (так проверяется письмо от
  GitHub) разбудил бы людей настоящей тревогой.

Поэтому: история для решения «писать или молчать» запрашивается с `event=schedule`,
ручной прогон в Telegram молчит (осознанно проверить сам путь отправки — галочка
`notify` при запуске), а его отметка в приложении помечается как ручная.

У ручного запуска есть поле `url`: адрес для диагностики вместо боевого.

## Кто сторожит сторожа

Внешний монитор не может сообщить о собственном выключении: тишина от него
неотличима от «всё хорошо». Поэтому после каждого удачного обхода он отмечается
в приложении — `POST /api/monitor/ping?source=schedule|manual` с заголовком
`X-Monitor-Token`. Ручка пишет только время, три строки в `SyncState`:

| Ключ | Что значит |
| --- | --- |
| `monitor:external` | последний заход любым способом |
| `monitor:external:schedule` | последний заход **по расписанию** — именно он считается наблюдением |
| `monitor:external:first` | самый первый заход, не переписывается никогда |

Дальше их читает `observe-local.sh`:

| Состояние | Реакция |
| --- | --- |
| по расписанию заходили меньше 3 часов назад | норма |
| по расписанию не заходили дольше 3 часов | инцидент |
| по расписанию не заходили ни разу, но первый заход был меньше суток назад | предупреждение (расписание раскачивается) |
| по расписанию не заходили ни разу, а первому заходу больше суток | инцидент «расписание не сработало ни разу за N ч» |
| `MONITOR_PING_TOKEN` не задан | предупреждение «снаружи прод никто не проверяет» |

Отдельная строка про «последний заход любым способом» печатается обычным текстом:
она помогает понять, живой ли монитор вообще, но инцидентом не управляет — иначе
один ручной прогон раз в месяц маскировал бы выключенное расписание.

⚠️ **Расписание GitHub засыпает после 60 дней без коммитов в репозитории.**
Именно на этот случай и сделана обратная отметка: спящее расписание не молчит
незаметно, о нём напишет внутренняя проверка.

## Настройка

Секреты репозитория (`Settings → Secrets and variables → Actions`):

| Имя | Обязателен | Зачем |
| --- | --- | --- |
| `MONITOR_PING_TOKEN` | да | обратная отметка; то же значение лежит в `/opt/mnenezhalko/shared/.env` |
| `MONITOR_BOT_TOKEN` | нет | токен ОТДЕЛЬНОГО бота для тревог |
| `MONITOR_CHAT_ID` | нет | кому писать (можно несколько через запятую) |

Переменная `MONITOR_URL` (Variables, не Secrets) переопределяет адрес прода;
по умолчанию — боевой.

Прогнать руками:

```bash
gh workflow run uptime.yml                              # обычный диагностический прогон
gh workflow run uptime.yml -f url=https://example.invalid  # намеренно неудачный
gh workflow run uptime.yml -f notify=true               # проверить путь отправки в Telegram
gh run list --workflow=uptime.yml                       # что показали последние обходы
node scripts/uptime-check.mjs                           # локально, если адрес прода резолвится
```

**Письмо от GitHub стоит проверить один раз намеренно**, пока бота для тревог нет:
запустить с заведомо сломанным `url`, дождаться красной джобы и убедиться, что письмо
пришло (`Settings → Notifications → Actions`, «Send notifications for failed workflows
only»). Пока это не проверено, единственный канал пробуждения человека держится
на непроверенной настройке почты.

⚠️ С рабочей машины на Windows домен `sslip.io` не резолвится вовсе — локальный
прогон делать с сервера или через `gh workflow run`.

## Чего не увидит и он

- **Поломку самого GitHub Actions.** Тогда обхода не будет; заметит внутренняя
  проверка по отсутствию отметок.
- **Тихие внутренние поломки.** Зависшие письма, ошибки джоб, старый бэкап — это
  зона внутреннего watchdog'а: снаружи всё это выглядит здоровым.
- **Проблемы, видные только человеку**: сломанная вёрстка, неудачный текст,
  бот отвечает не то.
