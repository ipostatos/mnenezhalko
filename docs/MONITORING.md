# Внутренний watchdog: что он видит и чего не увидит

Появился 30 июля 2026 вместе с неделей наблюдения (`OBSERVATION_GATE.md`).
Это **внутренний** слой контроля: он живёт на той же машине, что и приложение.

## Что это такое

Раз в час systemd-таймер запускает проверку `scripts/observe-local.sh` и, если та
нашла инцидент, `scripts/observe-alert.sh` пишет администраторам в Telegram.

| Файл | Роль |
| --- | --- |
| `scripts/observe-local.sh` | Сама проверка. Работает на сервере, только читает: ни записи в базу, ни рестарта. Код возврата 1 — есть инцидент |
| `scripts/observe.sh` | Обёртка для ручного запуска с рабочей машины по SSH (`bash scripts/observe.sh`) |
| `scripts/observe-alert.sh` | Watchdog: прогон проверки, решение писать или молчать, отправка |
| `scripts/mnenezhalko-observe.service` | Единичный прогон, `SuccessExitStatus=0 1` (инцидент это не сбой проверки) |
| `scripts/mnenezhalko-observe.timer` | Раз в час, `Persistent=true`, `OnBootSec=5min`, `RandomizedDelaySec=3min` |

## Что он увидит

- служба не `active` или её перезапускал systemd (то есть процесс падал);
- `/api/health` не отвечает;
- письма о решениях модерации не доставлены после трёх попыток;
- книга зависла в `approving` дольше 30 минут;
- джоба планировщика записала ошибку;
- cookie Notion не работает или синк не проходил больше суток;
- свободного места меньше 800 МБ (релизы запрещены) или меньше 1,5 ГБ (предупреждение);
- бэкап старше 26 часов или его нет вовсе.

## Чего он НЕ увидит — и это важно

- **Смерть всей машины.** Нет машины — нет и проверки: никто не напишет.
- **Пропажу сети или блокировку исходящих.** Проверка пройдёт, отправка молча не дойдёт
  (в journal останется «не смог написать админу»).
- **Поломку самого Telegram API.** Тот же случай: отправить сообщение нечем.
- **Проблемы, которые видны только человеку**: сломанная вёрстка, неудачная формулировка,
  бот отвечает не то. Это ловится глазами и жалобами.

Поэтому настоящий **внешний** uptime-монитор (кто-то снаружи стучится в `/api/health`
и будит человека, когда ответа нет) остаётся отдельным следующим этапом. Внутренний
watchdog его не заменяет и не отменяет — он закрывает другой класс: тихие поломки
внутри работающего приложения, о которых иначе узнаёшь через неделю.

## Молчание важнее сообщений

Watchdog, который пишет каждый час об одном и том же, выключают на третий день,
и тогда он не сообщит уже ничего. Правила:

| Переход | Что делает |
| --- | --- |
| норма → инцидент | пишет сразу |
| тот же инцидент продолжается | молчит |
| тот же инцидент, 6 часов без решения | напоминает один раз, дальше снова молчит |
| набор инцидентов изменился (добавился новый) | пишет сразу |
| инцидент → норма | пишет один раз «снова в норме» |

Состояние лежит в `/opt/mnenezhalko/shared/monitoring/observe-state`: отпечаток строк
инцидентов, время начала и время последней отправки.

⚠️ Отпечаток считается по строкам «🔴» **с выбитыми числами**: «бэкап 29 ч назад»
и «бэкап 30 ч назад» это одна и та же проблема. Без этого каждый час приходило бы
сообщение «набор инцидентов изменился», то есть ровно тот спам, от которого правила и защищают.

## Что уходит в Telegram

```
🔴 МнеНеЖалко: инцидент наблюдения

• не доставлено писем о решениях после трёх попыток: 1
• последний бэкап 29 ч назад (cron в 3:34)

Релиз: 1e29b10
Версия: 0.2.0-beta.2
Время: 30.07.2026 09:45 Europe/Warsaw

Проверка:
systemctl status mnenezhalko
journalctl -u mnenezhalko -n 100
```

Только агрегаты и техника релиза. **Не уходит ничего личного**: ни имён, ни ников,
ни числовых id, ни текстов отзывов, ни причин ограничений, ни текста `lastError`
(там может оказаться название книги или ник — Telegram возвращает такое в ошибках).
Подробности печатаются обычными строками: они остаются в отчёте и в `journalctl`,
но в сообщение не попадают. На это есть отдельный тест.

Сообщение уходит **каждому** администратору независимо: недоставка одному
(заблокировал бота, не начинал диалог) не отменяет отправку остальным.

## Установка на сервере

Юниты ставятся один раз, дальше они подхватывают скрипты текущего релиза через
симлинк `current`:

```bash
install -d -m 755 /opt/mnenezhalko/shared/monitoring
cp /opt/mnenezhalko/current/scripts/mnenezhalko-observe.service /etc/systemd/system/
cp /opt/mnenezhalko/current/scripts/mnenezhalko-observe.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now mnenezhalko-observe.timer
```

Проверить:

```bash
systemctl list-timers mnenezhalko-observe.timer   # когда следующий запуск
systemctl start mnenezhalko-observe.service       # прогнать сейчас
journalctl -u mnenezhalko-observe -n 50           # что увидел
```

Разовый прогон вручную с рабочей машины (без отправки сообщений):
`bash scripts/observe.sh`.
