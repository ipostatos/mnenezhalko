### Сессия стабилизации: производительность, безопасность, чистка (этапы 0–8)

Отдельный заход после внешнего аудита. Принцип сессии: **ни одного «исправления по бумаге»** —
каждый баг сначала воспроизводился тестом, потом чинился, потом тест проверялся откатом фикса
(без фикса тест обязан падать). Тестов в проекте было 18, стало **80**, все зелёные в CI.

**Найдено и починено (то, чего никто не заметил бы до аварии):**

- **Дыра в ссылках-приглашениях на выдачу.** Ссылка `?start=loan_<id>` содержала сырой id выдачи
  (он же светился в API, событиях и Notion), а разбор «моих» выдач запускался при **каждом**
  `/start` и забирал все невостребованные выдачи по совпадению username. То есть человек,
  зарегистрировавший в Telegram чужой ник, одним `/start` получал чужие книги и право отметить их
  возвращёнными. Теперь одноразовый claim-токен (24 байта, в базе только sha256, срок 24 ч),
  привязка ровно к одной выдаче, при несовпадении ника отказ. Старые ссылки продолжают работать,
  но только для выдач без токена и только при совпадении ника.
- **Утечка геолокации из фотографий.** Фото книги сохранялось как прислано — с EXIF, включая GPS
  с телефона, — а ссылка на файл **публична** и уходит в общий Notion проекта. Теперь фото
  нормализуется при сохранении (поворот по EXIF, ресайз до 1600, webp, метаданные не переносятся).
- **Гонка при отмене возврата.** Проверка «книга не выдана другому» и сама запись были разными
  запросами к базе; конкурентная выдача успевала пролезть между ними, и на одной книге оказывались
  **две активные выдачи**. Воспроизведено тестом, закрыто транзакцией. Заодно `markReturned` тоже
  стал транзакционным: падение между шагами оставляло книгу занятой навсегда.
- **Обложки в `/api/loans` шли мимо всего конвейера** — без ресайза, без кэша и **без SSRF-проверки**,
  сырой чужой URL прямо в клиент.
- **Предохранитель синка маскировал сам себя.** Подозрительный прогон (когда «пропало» больше 15%
  библиотеки) всё равно двигал отметку «последний успешный», то есть скрывал ровно ту проблему,
  ради которой предохранитель и делался. Теперь отметка двигается только на честном прогоне,
  а книги и настолки синкаются независимо (падение одного источника не срывает второй).
- **DNS rebinding.** SSRF-проверка резолвила домен сама, а `fetch()` резолвил его **второй раз** —
  атакующий DNS с TTL=0 отдаёт публичный адрес на проверку и приватный на соединение. Теперь
  соединение «пришпилено» к уже проверенным адресам. Проверено эмпирически.
- **Лимит размера файла проверялся после полной загрузки в память** — сервер без `Content-Length`
  мог залить гигабайты до отказа. Теперь байты считаются по потоку, соединение рвётся на превышении.
- **Кэш обложек не чистился вообще** (на проде 181 МБ, 1510 файлов, 0 удалений). Добавлена уборка
  (60 дней / 2 ГБ, таймер раз в 6 ч, файлы младше 5 минут не трогаются).

**Производительность:**
- Один размер обложки 640px на все случаи заменён на три по реальному размеру отрисовки:
  списки 96, карточки 220, карусель 320.
- Витрина греется в фоне при смене ротации, а не первым живым посетителем.
- `docs/PERFORMANCE_BASELINE.md` — замеры сняты **с прода по SSH**, не из головы.

**Наблюдаемость:** заголовок `X-Image-Cache` различает HIT/MISS/NEGATIVE (раньше всё было «MISS»),
структурные логи без полного URL (в чужих CDN-ссылках бывают токены), админская ручка
`GET /api/admin/img-metrics` со счётчиками и размером кэша.

**Защита от регресса:** `showcase-budget.test.ts` поднимает настоящий Fastify и проверяет бюджеты —
возврат к 80 книгам в витрине или к оригиналам обложек вместо превью поймается тестом.

### Безопасность (по внешнему аудиту) — три серьёзные дыры закрыты, с тестами
- **Выдача только своей книги.** `createLoan()` теперь в транзакции проверяет владельца
  (`book.owner.tgId` == запросивший), что книга одобрена и свободна, и что нет второй активной
  выдачи. Раньше `bookId` брался из тела запроса на веру — подготовленным запросом можно было
  пометить занятой **чужую** книгу.
- **Предохранитель Notion-синка.** Если из активного набора «пропало» >15% книг (при объёме ≥20),
  массовая деактивация **пропускается**, синк помечается подозрительным, админам уходит
  предупреждение. Неполный, но формально успешный ответ неофициального Notion API больше не может
  скрыть половину библиотеки.
- **SSRF-фильтр обложек.** Новый `net.ts`: загрузка обложек только на **публичные** адреса (резолв
  DNS + проверка каждого адреса и каждого редиректа), приём `coverUrl` от пользователя отсекает
  приватные/служебные (`169.254.169.254`, `127.0.0.1`, `10/8`, …). Проверено вживую и на проде.
- **sharp 0.33 → 0.35.3** — закрыты libvips CVE-2026-33327/33328/35590/35591, `npm audit` чист.
- **Тесты** `server/src/security.test.ts` — **8** тестов: выдача своей книги (1), выдача чужой
  книги отклонена (1), повторная выдача той же книги отклонена (1), выдача неодобренной
  (pending) книги отклонена (1), выдача без `bookId` разрешена (1), предохранитель Notion-синка
  `deactivationGuard` (1), `isPrivateIp` (1), `isSafeCoverUrl` (1).
  Команда `npm test` в `server/` запускает **18** тестов — этот файл (8) вместе с
  `server/src/reminders.test.ts` (10, напоминания о возврате, не относится к безопасности).
  В CI проходят все 18/18, но «18» — это размер всего suite, а не одного security.test.ts.
- Коммит `869b33f`.

### Карусель: image pipeline + hotfix производительности
Проблема медленной карусели — не один запрос, а цепочка решений. Разобрано по слоям.

**Hotfix (без «тяжёлых» изменений):**
- Витрина сокращена **80 → 12** книг (меньше `<img>`, запросов, декодирования, DOM).
- Подборка **стабильна 30 минут** (memo по городу на сервере) — не новая случайная выборка на каждый заход.
- Центральная обложка и два соседа грузятся **приоритетно** (`eager` / `fetchpriority=high`), остальные лениво.
- Найденная поиском книга вставляется **в середину** ленты (не в начало) — карусель не прокручивается «через всю ленту»; далёкая цель — мгновенный переход, а не длинный smooth-scroll.
- Тактильный «щёлк» — **только при ручном** листании (при программном скролле молчит).
- `will-change` — только у карточек **у центра** (класс `near-center`), а не у всех.
- **Skeleton** фиксированной высоты до загрузки витрины — без визуального скачка.

**Image pipeline (замена «кэша оригиналов» на конвейер):**
- `/api/img` теперь **ресайзит в webp-превью** нужной ширины (карусель — 320px, карточки — 640px) через **sharp**, а не отдаёт оригинал. Обложки livelib по 2-3 МБ → превью ~30-40 КБ.
- **Дедупликация in-flight**: 8 одновременных запросов одной обложки = одна внешняя загрузка (проверено).
- **Лимит 4** одновременных внешних скачиваний (холодный кэш карусели больше не бомбит чужие CDN).
- **Негативный кэш** (1 ч) для битых/недоступных — не долбим origin на каждый заход.
- Ширина входит в **HMAC-подпись** и в ключ файла кэша.
- **Метрики** в ответе `/api/img`: `X-Image-Cache: HIT|MISS`, `X-Image-Origin`, `Server-Timing: img;dur=…` — чтобы мерить реальные p50/p95, а не один локальный замер.
- Коммит: *(этот)*. ⚠️ Прежняя оценка «50–500×» в разделе ниже была **локальным микрозамером** одного файла, а не p50/p95 у пользователей Telegram; теперь для реального замера есть заголовки.

### Импорт по ISBN
- В `/import` строка, похожая на ISBN, автоматически подтягивает **название, автора и обложку**.
- Источник — **OpenLibrary** (Books API, отдаёт авторов именами). Google Books оставлен запасным:
  без ключа он отвечает `429` (лимит) даже с IP сервера, поэтому OpenLibrary идёт первым.
- ⚠️ Русские издания в OpenLibrary покрыты слабо — такие пока добавляются вручную по названию.
- Коммиты: `729fee2`, `ce750d6`.

### Добавление книг админом «от имени» библиотекаря
- Команда `/onbehalf @ник` включает режим: всё, что админ добавляет дальше (фото, альбом, список,
  ISBN), записывается **на полку указанного библиотекаря**, а не админа.
- Город берётся у целевого библиотекаря (не спрашивается), в аудите остаётся, что добавил админ.
- `/onbehalf off` — выключить режим. Коммит `729fee2`.
